## Context

Ethico wants engineers to use the SonarQube MCP through GitHub Copilot without installing Docker locally. The registry (this repo) already documents the intended architecture from prior research (commit `5bc588d`): a centrally hosted, internal-only Azure Container App that developers reach over VPN, using per-developer `Authorization: Bearer <token>` — see [docs/sonarqube-deployment.md](/docs/sonarqube-deployment.md) and the "SonarQube" section of [README.md](/README.md).

This work is tracked by NWOW work item **#134516 - Add SonarQube MCP Server** (time/7Pace), with the actual work tracked via a GitHub issue in this repo — continuing the pattern used for Figma (#100587) and Angular/MS Learn (#98850).

  A scheduled (daily) Azure DevOps pipeline (living at `devops/Pipelines/SonarQubeMCP/` — see the corrected repo-location decision above) will poll the SonarQube Web API (`api/users/search` + `api/user_tokens/search?login=<user>`, using an admin token stored as a pipeline secret) for `mcp-*` tokens specifically — filtering out unrelated tokens like the 5 found above is essential now that we know they exist. `daysRemaining` is computed as a whole-calendar-day difference (time-of-day truncated/ignored everywhere) — this makes every checkpoint below an exact-match condition that naturally fires exactly once, with no persisted "already notified" state needed anywhere in the design:

  - **`daysRemaining` = 14, 3, 2, or 1** → "expiring soon" reminder, emailed to the token's owner directly only. No ops involvement — this is a routine, expected renewal, not a policy violation. Pipeline log records `"sent reminder to <First> <Last> for <token name>"` — name and token only, never the email address itself. If the owner has no email on file in SonarQube, falls back to notifying `ethico-infra@ethico.com` instead (nobody else to reach).
  - **`daysRemaining` = -1** → "your token has expired" message, same developer-only/fallback treatment as above, sent exactly once. Deliberately *not* also checking `daysRemaining == 0` with a same-day time-of-day comparison (which would catch a token expiring earlier that same day, before the pipeline's run) — the developer already gets an immediate, organic signal the moment it actually expires (their next MCP request fails with a 401), so a next-day backstop notification loses nothing meaningful while keeping every check in the entire pipeline pure date-only, with zero time-of-day logic anywhere.
  - **No expiration set at all** (a separate, unrelated condition) → a policy violation, so ops needs visibility: **To:** `ethico-infra@ethico.com`, **Cc:** the token owner (if they have an email on file — otherwise `ethico-infra@ethico.com` only, noting the owner couldn't be looped in). Unlike the expired-token case, ops has an actual governance/escalation role here since Developer Edition can't prevent this at creation time and no one but an admin can force a fix.

  **Known, accepted limitation (considered and deliberately not fixed, 2026-09-02):** every check above is scoped to `mcp-*`-named tokens, because SonarQube exposes no signal beyond a token's own name to tell what it's actually used for. A developer whose MCP token doesn't follow the `mcp-<username>` naming convention is invisible to this pipeline entirely — no reminder, no expired notice, no no-expiration flag. A fix was drafted (widen the no-expiration check to every token org-wide, with a hardcoded ignore list for known-good non-expiring tokens like CI service accounts) but rejected: that ignore list would need to name specific accounts and token labels in `devops`-repo source control, which is readable far more broadly than SonarQube's own admin screens — cataloging exactly which credentials never expire in a widely-readable location was judged not worth the reconnaissance value it hands anyone who gains even minor access to that repo. The real mitigation is process, not tooling: the README's naming-convention instruction is what this pipeline's coverage actually depends on.

  Adapt the existing pipeline-driven email pattern from `devops/Vulnerability_Scan/sendemail_scan.ps1` (PowerShell + `System.Net.Mail.SmtpClient` against AWS SES's SMTP interface, credentials from a variable group) rather than hand-rolling new email-sending logic.

### Known bug to fix along the way

The registry files committed in `5bc588d` describe the SonarQube entry as a **stdio** package (`docker run ... -e SONARQUBE_TOKEN -e SONARQUBE_URL`), but the actual architecture is an **HTTP remote** with a per-developer Bearer token — same pattern as the Figma/Microsoft Learn entries (`executionModel: "remote-http"` + `remotes: [...]`). This needs correcting to the real Container App URL, or the registry will tell VS Code to try to run Docker locally instead of connecting to the hosted server.

## Verification Steps

1. **[Phase 1] Image provenance** — confirm the running Container App revision references the ACR image (by digest), not Docker Hub directly; confirm the Trivy scan report for that digest shows no unaddressed High/Critical findings.
2. **[Phase 1] Infra reachability** — from a VPN-connected machine: `curl https://<container-app-fqdn>/health` returns HTTP 200 with an empty body; `curl https://<container-app-fqdn>/info` returns `{"version":"1.24.0"}` (updated from `1.20.0` — see task #3's version-bump decision).
3. **[Phase 1] Ingress isolation** — from a network NOT on VPN (e.g. phone hotspot), confirm the same URL fails to resolve/connect, proving internal-only ingress is actually enforced.
4. **[Phase 2] Alerting fires** — deliberately stop the container app (or push a bad revision) briefly and confirm the health-check alert fires and the notification email arrives. (New Relic clause removed — cut 2026-08-26, see Monitoring decision above.)
5. **[Phase 2] Pipeline dry run** — trigger the ADO pipeline against a no-op version bump (or a test tag) and confirm it completes pull → scan → promote → deploy → verify end-to-end without manual intervention.
6. **[Phase 1] Functional / end-to-end** — point `mcp.json` (VS Code) or `claude mcp add` (Claude Code) at the real URL with your own real SonarQube USER token (per [README.md](/README.md)) and ask it to list open issues for a real project on `https://sqdev.mycompliancemanagement.com`; confirm results return in **both** clients, not just one. **Partial progress (2026-09-02), not complete:** a raw JSON-RPC `initialize` handshake via curl from `CL-DEV-A01` succeeded and returned real server info — confirms the FQDN, token, and MCP server all work at the protocol level, but this is not a real client and not a meaningful tool call. This step stays open until an actual VS Code or Claude Code session gets a real result back.
7. **[Phase 1] Read-only + token governance enforcement** — attempt a write-style action (e.g. resolving an issue) through the MCP and confirm it's rejected (`SONARQUBE_READ_ONLY=true`); confirm a SonarQube Project token or Global Administrator token is rejected (only USER tokens should work); confirm the request shows up in SonarQube's audit log tied to your specific token.
8. **[Phase 1] Registry correctness** — after task #8, validate both JSON files parse, that VS Code's `@mcp` picker shows SonarQube as a remote-HTTP server (not attempting a local `docker run`), and that `claude mcp list` shows a working `sonarqube` entry.
9. **[Phase 2] Token docs are actually followable** — have one of the pilot volunteers (someone who hasn't seen the internal design docs) follow only the README's token-generation section cold, with no extra help, and confirm they can generate their own USER token and get a working connection from it in whichever client they use.
10. **[Phase 2] Token expiry reminders work** — generate a test `mcp-*` token with a near-term expiration date, run the scheduled pipeline manually, and confirm the reminder email arrives for that token before it expires.
