# Deploy SonarQube MCP Server to Azure (Container Apps) + Monitoring

Location/naming here loosely follows the `specs/<work-item-id>-<slug>/` convention seen elsewhere in the org (e.g. `policy-management`), without adopting the full GitHub spec-kit tool scaffolding (`.specify/`, `constitution.md`, etc.) — just the folder convention for discoverability.

## Context

Ethico wants engineers to use the SonarQube MCP through GitHub Copilot without installing Docker locally. The registry (this repo) already documents the intended architecture from prior research (commit `5bc588d`): a centrally hosted, internal-only Azure Container App that developers reach over VPN, using per-developer `Authorization: Bearer <token>` — see [docs/sonarqube-deployment.md](/docs/sonarqube-deployment.md) and the "SonarQube" section of [README.md](/README.md).

This work is tracked by NWOW work item **#134516 - Add SonarQube MCP Server** (time/7Pace), with the actual work tracked via a GitHub issue in this repo — continuing the pattern used for Figma (#100587) and Angular/MS Learn (#98850).

### Decisions confirmed so far

- **SonarQube Server** (public, reachable from anywhere): `https://sqdev.mycompliancemanagement.com/` — no new network peering needed for outbound reachability.
- **Target subscription**: confirmed — **Azure DevTest subscription 1** (`326c5c7f-73c8-4e8b-b146-d643c06ced0d`, tenant `complianceline.com` / `b3f8ea1b-fcb5-4178-b14c-7625dd8865ca`).
- **Image supply chain**: pull `sonarsource/sonarqube-mcp` from Docker Hub, Trivy-scan it (per the existing policy in [docs/mcp-maintenance.md](/docs/mcp-maintenance.md)), then push the vetted image into a new **Azure Container Registry (ACR)** we control, pinned by digest. The Container App pulls from ACR, not Docker Hub directly — gives an audit trail and isolates us from upstream tag mutation/outages.
- **Update mechanism**: an **Azure DevOps Pipeline**, living in the `devops` repo at `Pipelines/SonarQube/` (per that repo's `/Pipelines/<Capability>` convention — see `devops/CLAUDE.md` and its `.claude/knowledge/pipeline-requirements.md` §2), owns the "pull → scan → promote to ACR → deploy → verify" flow, replacing the manual `az containerapp update` steps currently written in the maintenance doc. Needs an Azure Resource Manager service connection from ADO into the target subscription (scoped to the resource group, granting rights to ACR + the Container App) — as the org's Azure DevOps organization owner, Walter can create this himself; no separate approval or handoff needed. Note: `devops/Vulnerability_Scan/templates/` only covers .NET (NuGet) and npm dependency scanning today — there is no existing Docker/container-image scan template to reuse, so the Trivy step is new, first-of-its-kind pipeline work, not a drop-in. The deploy step itself should call the existing `devops/Azure/UpdateAzureContainer_WithEnv.ps1` (diffs an `appsettings_envmapping.json` against the live revision's env vars, then runs `az containerapp update --image ... --revision-suffix ... --replace-env-vars`) rather than hand-rolling new CLI calls — the build side of the pipeline needs to emit an `appsettings_envmapping.json` artifact for the SonarQube MCP's env vars (no KeyVault secrets needed; there's no shared token). The Bicep from task #4 belongs in `devops/infrastructure/SonarQube/` — a workload-scoped IaC folder living parallel to `Pipelines/SonarQube/`, following standard Bicep practice of organizing by deployable unit rather than resource type. (`devops/Azure/Bicep/provision_StorageAccount.bicep` was a one-off attempt at a reusable templated Bicep pattern, not an established repo convention — don't treat its flat, resource-type-named layout as precedent.)
- **Developer authentication**: already the right design — the Container App is stateless and holds no shared SonarQube token. Each developer generates their **own SonarQube USER token** (via the SonarQube UI: *My Account → Security → Generate Tokens*, using a `mcp-<username>` naming convention so it's distinguishable from other tokens like CI/CD scanner tokens) and adds it to their own local `mcp.json` as `Authorization: Bearer <token>`. This gives per-developer usage tracking for free via SonarQube's own audit/access logs (no shared/global token).
- **Token expiration & rotation**: as SonarQube admin, set a global max token lifetime under *Administration → Configuration → Security* so no MCP token can be created without an expiration date. SonarQube doesn't natively email users before a token expires, so a scheduled Azure DevOps pipeline (also living at `devops/Pipelines/SonarQube/`) will poll the SonarQube Web API (`api/users/search` + `api/user_tokens/search?login=<user>`, using an admin token stored as a pipeline secret) for `mcp-*` tokens nearing expiration and email the owner ahead of time. **Not** the Azure Monitor Action Group used for Container App alerts — that targets a fixed ops distribution list, not individual developers. Instead, adapt the existing pipeline-driven email pattern from `devops/Vulnerability_Scan/sendemail_scan.ps1` (PowerShell + `System.Net.Mail.SmtpClient` against AWS SES's SMTP interface, credentials from a variable group) to send a per-developer reminder instead of a single fixed-recipient report.
- **Monitoring**: Azure Monitor + Action Group email as the baseline. New Relic is used org-wide for dev/prod monitoring, but this will be Ethico's **first Azure→New Relic integration**, so budget real time for it rather than assuming it's a copy-paste of an existing pattern.
- **Rollout**: pilot first (you + 1-2 volunteers) before an org-wide announcement.

### Known bug to fix along the way

The registry files committed in `5bc588d` describe the SonarQube entry as a **stdio** package (`docker run ... -e SONARQUBE_TOKEN -e SONARQUBE_URL`), but the actual architecture is an **HTTP remote** with a per-developer Bearer token — same pattern as the Figma/Microsoft Learn entries (`executionModel: "remote-http"` + `remotes: [...]`). This needs correcting to the real Container App URL, or the registry will tell VS Code to try to run Docker locally instead of connecting to the hosted server.

## Verification Steps

1. **Image provenance** — confirm the running Container App revision references the ACR image (by digest), not Docker Hub directly; confirm the Trivy scan report for that digest shows no unaddressed High/Critical findings.
2. **Infra reachability** — from a VPN-connected machine: `curl https://<container-app-fqdn>/health` returns HTTP 200 with an empty body; `curl https://<container-app-fqdn>/info` returns `{"version":"1.20.0"}`.
3. **Ingress isolation** — from a network NOT on VPN (e.g. phone hotspot), confirm the same URL fails to resolve/connect, proving internal-only ingress is actually enforced.
4. **Alerting fires** — deliberately stop the container app (or push a bad revision) briefly and confirm the health-check alert fires and the notification email arrives; confirm New Relic also reflects the outage.
5. **Pipeline dry run** — trigger the ADO pipeline against a no-op version bump (or a test tag) and confirm it completes pull → scan → promote → deploy → verify end-to-end without manual intervention.
6. **Functional / end-to-end** — from VS Code, point `mcp.json` at the real URL with your own real SonarQube USER token (per [README.md](/README.md)) and ask Copilot Chat to list open issues for a real project on `https://sqdev.mycompliancemanagement.com`; confirm results return.
7. **Read-only + token governance enforcement** — attempt a write-style action (e.g. resolving an issue) through the MCP and confirm it's rejected (`SONARQUBE_READ_ONLY=true`); confirm a SonarQube Project token or Global Administrator token is rejected (only USER tokens should work); confirm the request shows up in SonarQube's audit log tied to your specific token.
8. **Registry correctness** — after task #8, validate both JSON files parse and that VS Code's `@mcp` picker shows SonarQube as a remote-HTTP server (not attempting a local `docker run`).
9. **Token docs are actually followable** — have one of the pilot volunteers (someone who hasn't seen the internal design docs) follow only the README's token-generation section cold, with no extra help, and confirm they can generate their own USER token and get a working connection from it.
10. **Token expiry reminders work** — generate a test `mcp-*` token with a near-term expiration date, run the scheduled pipeline manually, and confirm the reminder email arrives for that token before it expires.
