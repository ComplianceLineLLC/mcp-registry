# Deploy SonarQube MCP Server to Azure (Container Apps) + Monitoring

> Tracked by NWOW work item **#134516 - Add SonarQube MCP Server**. Location/naming here loosely follows the `specs/<work-item-id>-<slug>/` convention seen elsewhere in the org (e.g. `policy-management`), without adopting the full GitHub spec-kit tool scaffolding (`.specify/`, `constitution.md`, etc.) — just the folder convention for discoverability.

## Context

Ethico wants engineers to use the SonarQube MCP through GitHub Copilot without installing Docker locally. The registry (this repo) already documents the intended architecture from prior research (commit `5bc588d`): a centrally hosted, internal-only Azure Container App that developers reach over VPN, using per-developer `Authorization: Bearer <token>` — see [docs/sonarqube-deployment.md](/docs/sonarqube-deployment.md) and the "SonarQube" section of [README.md](/README.md).

This work is tracked by NWOW work item **#134516 - Add SonarQube MCP Server** (time/7Pace), with the actual work tracked via a GitHub issue in this repo — continuing the pattern used for Figma (#100587) and Angular/MS Learn (#98850).

### Decisions confirmed so far

- **SonarQube Server** (public, reachable from anywhere): `https://sqdev.mycompliancemanagement.com/` — no new network peering needed for outbound reachability.
- **Target subscription**: confirmed — **Azure DevTest subscription 1** (`326c5c7f-73c8-4e8b-b146-d643c06ced0d`, tenant `complianceline.com` / `b3f8ea1b-fcb5-4178-b14c-7625dd8865ca`).
- **Image supply chain**: pull `sonarsource/sonarqube-mcp` from Docker Hub, Trivy-scan it (per the existing policy in [docs/mcp-maintenance.md](/docs/mcp-maintenance.md)), then push the vetted image into a new **Azure Container Registry (ACR)** we control, pinned by digest. The Container App pulls from ACR, not Docker Hub directly — gives an audit trail and isolates us from upstream tag mutation/outages.
- **Update mechanism**: an **Azure DevOps Pipeline** owns the "pull → scan → promote to ACR → deploy → verify" flow, replacing the manual `az containerapp update` steps currently written in the maintenance doc. Needs an Azure Resource Manager service connection from ADO into the target subscription (scoped to the resource group, granting rights to ACR + the Container App) — as the org's Azure DevOps organization owner, Walter can create this himself; no separate approval or handoff needed. Note: `devops/Vulnerability_Scan/templates/` only covers .NET (NuGet) and npm dependency scanning today — there is no existing Docker/container-image scan template to reuse, so the Trivy step is new, first-of-its-kind pipeline work, not a drop-in. The deploy step itself should call the existing `devops/Azure/UpdateAzureContainer_WithEnv.ps1` (diffs an `appsettings_envmapping.json` against the live revision's env vars, then runs `az containerapp update --image ... --revision-suffix ... --replace-env-vars`) rather than hand-rolling new CLI calls — the build side of the pipeline needs to emit an `appsettings_envmapping.json` artifact for the SonarQube MCP's env vars (no KeyVault secrets needed; there's no shared token).
  - **Correction (2026-08-11): both the Bicep and the pipeline YAML live in *this* repo, not `devops`.** The original plan assumed a `devops/Pipelines/<Capability>` + `devops/infrastructure/<Capability>` convention citing `devops/CLAUDE.md` — that file doesn't exist on `devops`'s `Develop` branch. It does exist on Walter's own unmerged branch (`wbates/126802-Add-docs-for-pipeline-requirements`), and it says the opposite: `devops` is explicitly carved out as shared-templates-only ("hosts shared Azure DevOps pipeline tooling... does not build application code itself"); each app owns its own `/Pipelines` in its own repo. Since `mcp-registry` isn't a single app but a registry of many MCP servers, new decision: an app-scoped subfolder per hosted MCP to avoid mixing — Bicep now lives at [infrastructure/SonarQubeMCP/](../../infrastructure/SonarQubeMCP/) (already authored: `main.bicep` at subscription scope + `modules/` for the ACR, a user-assigned managed identity, and its `AcrPull` role assignment), and the pipeline YAML (task #7) will follow the same pattern at `Pipelines/SonarQubeMCP/`. `devops` stays referenced only for genuinely shared pieces: `Azure/UpdateAzureContainer_WithEnv.ps1` and possibly a new reusable Trivy template under `Vulnerability_Scan/templates/` if that becomes the shared pattern for other repos too.
  - Also decided: the Container App's identity is a **user-assigned** managed identity (`ethico-sonarqube-mcp-mi-dev`, provisioned in task #3's Bicep), not system-assigned — chosen for auditability and so its `AcrPull` grant survives if the Container App itself is ever recreated, at the cost of one extra resource to manage. Deliberately **not** using ACR's newer Entra ABAC repository-scoped permissions (confirmed real and GA via Microsoft Learn, not preview) — reusing an existing shared ACR (`ethicodev` in the Pay-As-You-Go Dev/Test subscription, which already holds 6 unrelated repos with zero existing scope-map isolation) would need a disruptive registry-wide migration affecting other teams' live workloads, and ABAC on a single-purpose new registry has no one else to isolate from.
- **Developer authentication**: already the right design — the Container App is stateless and holds no shared SonarQube token. Each developer generates their **own SonarQube USER token** (via the SonarQube UI: *My Account → Security → Generate Tokens*, using a `mcp-<username>` naming convention so it's distinguishable from other tokens like CI/CD scanner tokens) and adds it to their own local `mcp.json` as `Authorization: Bearer <token>`. This gives per-developer usage tracking for free via SonarQube's own audit/access logs (no shared/global token).
- **Token expiration & rotation**: as SonarQube admin, set a global max token lifetime under *Administration → Configuration → Security* so no MCP token can be created without an expiration date. SonarQube doesn't natively email users before a token expires, so a scheduled Azure DevOps pipeline (also living at `devops/Pipelines/SonarQube/`) will poll the SonarQube Web API (`api/users/search` + `api/user_tokens/search?login=<user>`, using an admin token stored as a pipeline secret) for `mcp-*` tokens nearing expiration and email the owner ahead of time. **Not** the Azure Monitor Action Group used for Container App alerts — that targets a fixed ops distribution list, not individual developers. Instead, adapt the existing pipeline-driven email pattern from `devops/Vulnerability_Scan/sendemail_scan.ps1` (PowerShell + `System.Net.Mail.SmtpClient` against AWS SES's SMTP interface, credentials from a variable group) to send a per-developer reminder instead of a single fixed-recipient report.
- **Monitoring**: ~~Azure Monitor + Action Group email as the baseline, New Relic as an additive org-wide layer~~ → **Correction (2026-08-26): New Relic dropped entirely.** Manager-level decision to avoid paying twice for the same telemetry, and to not block developer usability on a monitoring integration. Azure Monitor (task #4's Log Analytics workspace + task #5's alert rules/Action Group) was already the designated baseline — cutting New Relic doesn't leave a monitoring gap, it just removes the additive layer. Note for expectation-setting: true Application Insights-style APM (request/dependency tracing) needs code-level instrumentation, which isn't available for a vendor-supplied container we don't build — Log Analytics + Container Apps platform metrics is the realistic ceiling here, not a gap introduced by dropping New Relic. Task #6 is cut; the one piece of cleanup it left behind (revoking `NewRelic-Integrations`'s Reader role on `rg-ethico-sonarqube-mcp-dev`, granted during its now-abandoned front-loaded work) is deferred to Phase 2 — not urgent, isn't impeding anything, and doesn't need to happen before the rest of the cleanup.
- **Rollout**: pilot first (you + 1-2 volunteers) before an org-wide announcement.

### Known bug to fix along the way

The registry files committed in `5bc588d` describe the SonarQube entry as a **stdio** package (`docker run ... -e SONARQUBE_TOKEN -e SONARQUBE_URL`), but the actual architecture is an **HTTP remote** with a per-developer Bearer token — same pattern as the Figma/Microsoft Learn entries (`executionModel: "remote-http"` + `remotes: [...]`). This needs correcting to the real Container App URL, or the registry will tell VS Code to try to run Docker locally instead of connecting to the hosted server.

## Verification Steps

1. **[Phase 1] Image provenance** — confirm the running Container App revision references the ACR image (by digest), not Docker Hub directly; confirm the Trivy scan report for that digest shows no unaddressed High/Critical findings.
2. **[Phase 1] Infra reachability** — from a VPN-connected machine: `curl https://<container-app-fqdn>/health` returns HTTP 200 with an empty body; `curl https://<container-app-fqdn>/info` returns `{"version":"1.24.0"}` (updated from `1.20.0` — see task #3's version-bump decision).
3. **[Phase 1] Ingress isolation** — from a network NOT on VPN (e.g. phone hotspot), confirm the same URL fails to resolve/connect, proving internal-only ingress is actually enforced.
4. **[Phase 2] Alerting fires** — deliberately stop the container app (or push a bad revision) briefly and confirm the health-check alert fires and the notification email arrives. (New Relic clause removed — cut 2026-08-26, see Monitoring decision above.)
5. **[Phase 2] Pipeline dry run** — trigger the ADO pipeline against a no-op version bump (or a test tag) and confirm it completes pull → scan → promote → deploy → verify end-to-end without manual intervention.
6. **[Phase 1] Functional / end-to-end** — point `mcp.json` (VS Code) or `claude mcp add` (Claude Code) at the real URL with your own real SonarQube USER token (per [README.md](/README.md)) and ask it to list open issues for a real project on `https://sqdev.mycompliancemanagement.com`; confirm results return in **both** clients, not just one.
7. **[Phase 1] Read-only + token governance enforcement** — attempt a write-style action (e.g. resolving an issue) through the MCP and confirm it's rejected (`SONARQUBE_READ_ONLY=true`); confirm a SonarQube Project token or Global Administrator token is rejected (only USER tokens should work); confirm the request shows up in SonarQube's audit log tied to your specific token.
8. **[Phase 1] Registry correctness** — after task #8, validate both JSON files parse, that VS Code's `@mcp` picker shows SonarQube as a remote-HTTP server (not attempting a local `docker run`), and that `claude mcp list` shows a working `sonarqube` entry.
9. **[Phase 2] Token docs are actually followable** — have one of the pilot volunteers (someone who hasn't seen the internal design docs) follow only the README's token-generation section cold, with no extra help, and confirm they can generate their own USER token and get a working connection from it in whichever client they use.
10. **[Phase 2] Token expiry reminders work** — generate a test `mcp-*` token with a near-term expiration date, run the scheduled pipeline manually, and confirm the reminder email arrives for that token before it expires.
