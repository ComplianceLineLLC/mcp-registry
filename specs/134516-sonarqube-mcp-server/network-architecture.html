New finding (2026-08-28): ingress routing, not just DNS

What we found — A request sent directly to the environment's static IP (20.0.3.165), from CL-DEV-A01 — a VM natively inside clDEVvNET itself, no peering or VPN involved — with the exact correct hostname in both the TLS SNI and the HTTP Host header, is rejected by Azure's platform with a generic 404: "This Container App is stopped or does not exist." Verbose curl output confirms this is a real, direct TCP+TLS connection to our own environment's IP — not a DNS, proxy, or wrong-endpoint artifact.
What we've ruled out — The app itself is healthy: its own logs show a clean startup, and a wget --spider run from inside the running container confirmed it can reach out to sqdev.mycompliancemanagement.com through the NVA without issue. Azure's control plane agrees — revision Healthy/Running, 100% traffic weight, ingress config exactly as intended. So this isn't an app problem, and it isn't (only) a DNS problem — DNS was bypassed entirely for this test via curl --resolve, confirmed with -v to actually be connecting to 20.0.3.165 with no proxy involved.
Leading theory — The subnet's route table sends all 0.0.0.0/0 traffic to the NVA at 10.2.3.4. Microsoft's own Container Apps docs specifically warn: "You must allow traffic to the AzurePlatformDNS service tag (which includes 168.63.129.16). Blocking this service tag prevents your Container Apps environment from functioning correctly." We already confirmed the app's own outbound calls work fine through the NVA — but the platform's internal ingress-to-replica routing is a separate mechanism, and may depend on reaching that same platform IP (or others) that the current UDR could be interfering with.
Why this may be new territory, not a regression — Every one of the other 8 Container Apps environments already in clDEVvNET is external. Ours is the first internal one ever deployed here. Internal environments use a genuinely different mechanism — an actual Azure internal load balancer — so the existing NVA-routed UDR pattern (which works fine for 5 sibling external environments) has simply never been exercised against this specific architecture before now.
We tried to capture this directly — and the absence of data is itself informative — Enabled ContainerAppHTTPLogs and ContainerAppSystemLogs (platform-level diagnostic categories on the environment) specifically to see what Azure's edge proxy did with these requests. Re-ran the same rejected request three separate times over 15+ minutes: zero events landed in either table. This isn't a "still propagating" result — a different, pre-existing log pipe on this same environment (console/system logs via appLogsConfiguration) reliably shows new data within minutes, so the tooling and workspace are confirmed working. The likely reading: these requests are rejected at a layer before Container Apps' own per-app request logging ever sees them — consistent with a generic, platform-wide "no app matched" response rather than something our specific environment's ingress processes and logs.
What we need from you — Can you check whether the NVA correctly passes through AzurePlatformDNS (168.63.129.16) and any other Azure platform-management traffic Container Apps depends on internally? And separately — does an internal Container Apps environment need a different egress arrangement entirely (e.g. more like EmployeePortal-Dev-Subnet's direct-egress pattern) rather than the shared NVA-routed one the majority of subnets use? This is now the higher-priority question — the DNS Private Zone gap noted below still needs to happen eventually, but it's moot until ingress itself is confirmed working.

Still-needed follow-up (secondary — see the ingress finding above first)

DNS resolution for the internal Container App — Separate from today's ingress finding, we also confirmed the original assumption that Azure auto-provisions and links a Private DNS Zone for an internal Container Apps environment was wrong — confirmed via az network private-dns zone list (zero zones exist) and Microsoft's own docs, which describe this as a manual setup step.

Planned fix (still not implemented, still holding off until we hear from you): create a Private DNS Zone named thankfulmoss-c6ccc4d1.eastus.azurecontainerapps.io (matching the environment's own default domain) in our own resource group, with an A record *.internal → 20.0.3.165 (the environment's static IP), linked to clDEVvNET.

Open question: is a VNet link to clDEVvNET alone sufficient for a VPN-connected developer laptop to resolve this record, given the VPN gateway itself lives in the peered clUATvNET (different subscription)? There's no existing precedent in this org for a developer workstation resolving an Azure private DNS record over VPN. This question is now moot until the ingress finding above is resolved — even with perfect DNS, the same "app doesn't exist" response would come back, since that's happening at the IP level, before DNS is even a factor.
