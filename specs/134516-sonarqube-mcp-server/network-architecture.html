New open question for Gilbert

DNS resolution for the internal Container App — The original assumption that Azure auto-provisions and links a Private DNS Zone for an internal Container Apps environment was wrong — confirmed via az network private-dns zone list (zero zones exist) and Microsoft's own docs, which describe this as a manual setup step. Attempting curl against the Container App's FQDN from a VPN-connected machine fails with Could not resolve host.

Planned fix: create a Private DNS Zone named thankfulmoss-c6ccc4d1.eastus.azurecontainerapps.io (matching the environment's own default domain) in our own resource group, with an A record *.internal → 20.0.3.165 (the environment's static IP), linked to clDEVvNET.

Open question: is a VNet link to clDEVvNET alone sufficient for a VPN-connected developer laptop to resolve this record, given the VPN gateway itself lives in the peered clUATvNET (different subscription)? There's no existing precedent in this org for a developer workstation resolving an Azure private DNS record over VPN — the three private DNS zones that do exist today are for VNet-native app-to-database resolution, not developer-machine DNS. Plan is to create the zone/record/link first (unambiguously needed regardless of the VPN question) and re-test; if resolution still fails from VPN after that, this is the point to loop you in on VPN DNS forwarding specifically.
